# ADR 0007: Bounded worker supervision and private protocol v1

Status: The bounded Supervisor/Worker architecture was accepted for M4 on 2026-09-15; Gate 1 corrections recorded 2026-09-20 were subsequently approved. Gate 2 later routed production collection through the design, and the integrated semantics/privacy corrections passed targeted re-review. Controlled cancellation and calibrated internal timing were completed, followed by a passing final checkpoint-readiness review. M4 was checkpointed locally in `57abbec81ac8db83e04a2a588d39fe18c1650070` (`Milestone 4: bounded collection and controlled cancellation`). At the M4 checkpoint, no remote, push, tag, or release existed.

The existing in-process WMI and DisplayConfig calls can exceed nominal provider timeouts. The approved process boundary preserves completed independent facts while allowing the parent to stop accepting results and terminate a contained worker. Phase 1 exercised synthetic workers only; real production routing was introduced later in Gate 2.

## Deadlines and ownership

One monotonic `Deadline` is passed through a complete frame, including all partial prefix and payload reads. Every frame deadline is clipped to the operation deadline; progress never renews it. Acceptance requires full parsing, semantic/sequence validation and a state transition strictly before the deadline. Equality is timeout. Duration arithmetic saturates and native wait conversion caps at `uint.MaxValue - 1`; process-exit observation polls with a zero native wait.

The managed `NamedPipeServerStream` is retained over one owning `SafePipeHandle`. `PendingIo` owns the operation task, cancellation source, cancellation-completion task and drain-completion task. Timeout requests `CancelAsync` but does not await I/O completion without a separate deadline. It does not dispose the stream or release pending buffers. One absolute cleanup deadline covers termination, pending I/O completion and process-exit observation, clipped by the overall deadline, later active/cleanup reservations and final bookkeeping reserve. Disposal performs no additional wait.

If cleanup cannot be confirmed, or cleanup/disposal throws, the outcome is fatal. A locked process-lifetime `HostAdmission` latches poison and roots the entire unresolved session and task ownership until host exit. It has no reset API and no background reaper; another default supervisor shares the same latch. The lock protects admission/poison/quarantine state, never an I/O wait. Tests inject an isolated admission owner to avoid poisoning the test runner; a separate process probe verifies the actual default latch across new supervisors. Retention is intentional quarantine, not permission to continue collecting.

A skipped operation records timeout with zero attempts and leaves remaining operations eligible for evaluation. Current cleanup, each later active allowance and cleanup allowance, and final bookkeeping are reserved separately. Host cancellation stops subsequent operations, including when it arrives during accepted-result cleanup. Accepted operation data remains retained; a host-cancelled or fatal collection outcome may still veto continuation.

These are bounded supervisor waiting and ownership guarantees, tested with a manual clock and synthetic processes. They do not guarantee OS scheduling latency or cancellation of arbitrary synchronous native calls, and the calibrated budgets below are engineering choices with margins over one machine's measured maxima rather than a hard real-time bound. Production stayed on the original path during Phase 1; Gate 2 subsequently switched to `SupervisedWindowsCollector`. The old aggregate remains reference/test/shared mapping infrastructure.

## Creation-time containment and security

Before launch, read-only token inspection requires a non-elevated parent with mandatory integrity RID at or below medium (`0x2000`). Unverifiable security context, rejected deployment, containment setup failure and launch failure are fatal admission categories; no privilege adjustment, de-elevation or fallback occurs.

A fresh unnamed Job Object has kill-on-close, active-process limit one and no breakaway. `CreateProcessW` receives `JOB_LIST` and `HANDLE_LIST` at creation; there is no create-then-assign fallback. Attribute allocation and successful initialization are separate ownership states: initialization failure frees allocation only; initialized teardown deletes the list before freeing backing storage and releasing strong SafeHandle references. Those references remain live throughout `CreateProcessW`, including failure paths.

Exactly two handles are inherited: the same connected pipe-client handle is used for standard input and output, and a write-only NUL handle is used for standard error. Job, server pipe, process/token, console and unrelated inheritable handles are excluded. A synthetic inheritable event tests exclusion. The parent closes its client/NUL copies after attribute teardown.

The endpoint uses a random name, first-instance/one-instance byte mode, current-user DACL and remote-client rejection. The DACL is not authentication against hostile processes running as the same user; neither the pipe nor deployment hashes protect against an attacker who already controls that account or process. There is no reconnect, temporary-file IPC or permissive DACL fallback.

## Deployment and runtime identity

`worker-runtime-closure.ps1` derives files from the freshly built worker dependency manifest, including nested runtime targets. Project references build the worker before supervisor manifest generation (`CoreCompile`) and CLI/test deployment (`AfterTargets=Build`). Generation, copying and execution fingerprints share that closure and normalized relative paths. Validation hashes every manifest file recursively, including `runtimes/win/lib/net10.0/System.Management.dll`; it checks managed name/version/MVID, Windows case-insensitive uniqueness and traversal. Reparse points and unexpected non-PDB files are rejected. PDBs alone are excluded. Stale extras cause failure, are never blessed by enumeration, and are not silently deleted.

The parent runtime must have the recognized `shared/Microsoft.NETCore.App/<exact loaded version>` layout, with its loaded CoreLib there and explicit sibling `dotnet.exe`. Launch uses Windows quoting and `dotnet exec --fx-version <exact version> --roll-forward Disable`. There is no PATH search or alternate-host discovery. Parent-loaded Core/Windows/Protocol MVIDs and disk hashes must agree with the embedded worker manifest. Ready supplies protocol version, runtime version and Worker/Protocol/Core/Windows MVIDs; the parent compares them before sending any topology identities in Start. This detects stale/mixed builds, not malicious same-user file replacement or a fully compromised runtime.

## Protocol and preserved topology semantics

Protocol v1 uses a four-byte little-endian length followed by strict UTF-8 JSON. Order is Request (operation only) -> Ready (build identity) -> Start (operation input) -> one to three sequential AttemptStarted markers -> Result. WMI has one attempt; topology supports its existing three-attempt retry contract and a zero-attempt pre-query failure after Start. Maximum sequence length is seven frames. Request/Ready/AttemptStarted are bounded at 4 KiB; Start/Result at 1 MiB. Other limits remain 16K decoded string characters, depth 32 and 512 collection entries. All properties are required, unknown/duplicate fields are rejected and bound violations map to internal ResourceLimit without truncation.

Result validation checks operation, status/reason, non-null observations, provenance, available/unavailable combinations, topology labels/references, attempts, issues and field contradictions before acceptance. The optional monitor-name exception is restricted to exactly `unknown/null/missingValue`; `failed/null/missingValue`, `unsupported/null/missingValue` and other contradictory status/reason combinations are rejected even when a matching non-blocking issue is supplied. Genuine target-name failures remain valid with their correct failure/unsupported state, matching blocking issue and reason. Topology carries the complete existing `CollectorRun` and display observations, including partial/failed/unsupported states, retry diagnostics and exact adapter matches. Start permits inventory entries with an unavailable instance identity (`null`); they cannot be used as exact matches and no identity is fabricated. None of this changes public schema 0.2.0 or collector normalization.

## Evidence and next gate

### Post-Gate-2 correction note — 2026-09-21

This note records the later authorized integration corrections, not additional claims about the original Phase 1 implementation. Dispatch projects null/empty/whitespace WMI identities to protocol null without dropping rows or relaxing identity validation. WMI progress is emitted immediately before the fixed read. The existing topology loop owns retry progress immediately before each sizing call; progress transport exceptions escape without becoming native failures. Parent attempt counts reflect validated markers, not retrospective completion. Conditional driver omission removes one remaining reservation before topology without resetting the overall deadline or inventing a failure.

Protocol v1 now has one additional terminal control variant, `failure`, limited to `state: failed`, `reason: resourceLimit`, and an empty object payload. It is valid only after an attempt marker, for the current operation, and terminates the sequence. It uses the existing 4 KiB control bound; duplicate/unknown fields and other state/reason/payload combinations remain invalid. It replaces an oversized result rather than appending another result. The worker encodes once, catches only an encoding ResourceLimit, then sends a finite fixed fallback. Write failures are outside that catch and cannot trigger recursive retries. The parent applies the existing absolute deadline before classifying ResourceLimit and exports no fabricated native error or QueryPaths issue.

Validation fingerprints now include CLI deps/runtimeconfig, dependency-declared parent runtime/package assets, all project assemblies (including the embedded manifest-bearing Supervisor), recursive worker assets, selected dotnet path/file identity, and selected runtime version/directory/CoreLib identity. A metadata-only worker probe is invoked with the selected host and CLI deps/runtimeconfig; it performs no collection. Only the selected host and CoreLib are hashed from the framework installation. New evidence persists format-2 execution inputs and retains before/after comparisons. Historical M3 evidence is unchanged and limited to its originally recorded inputs.

Gate 2 adds real Worker dispatch for the five fixed operations and switches production CLI composition to `SupervisedWindowsCollector`. The Worker reuses the existing Windows mapping helpers; the parent reconstructs existing Core facts and joins, runs the driver operation only after available nonempty video inventory, passes transient GPU identities only as topology input, and preserves completed independent results across later failures/timeouts. Host-fatal admission/deployment/cleanup outcomes retain the safe no-preview path, while ordinary provider/timeout protocol outcomes remain reportable under the existing status/reason model.

See [validation evidence](../VALIDATION.md) for fresh results and the restricted-sandbox limitation, and [API feasibility](../API-FEASIBILITY.md) for native contracts. Schema 0.2.0, privacy projection and CLI exits remain unchanged. The targeted integrated semantics/privacy re-review passed on these corrections; the next gate was the authorized final pre-checkpoint phase recorded below.

### Final pre-checkpoint phase — 2026-09-21

Historical snapshot: handoff synchronization, measurement definitions, survivor/fingerprint/admission claims and numerical rationale below are superseded by the 2026-09-22 correction note and corrected validation record.

The targeted integrated semantics/privacy re-review passed on the corrections above. The authorized final phase then added two things and changed no contract already accepted here.

Controlled cancellation is now implemented. `HostCancellationController` counts interrupts and cancels on the first one; `Console.CancelKeyPress` is registered only around collection and only flips that state, performing no I/O or cleanup. The supervisor treats host cancellation like a failed operation for continuation purposes: result acceptance closes, later operations cannot start, accepted independent results stay internally retained, and cleanup reuses the one absolute cleanup deadline to terminate and confirm the in-flight worker. The CLI suppresses report preparation, preview and export, prints a plain cancellation notice and returns `3`; `host-cancelled` is an internal supervisor code that never becomes report state. A second interrupt leaves the default handler in place, so forced termination proceeds with no cleanup, exit-code or report promise. The creation-time job kill-on-close remains the containment backstop.

`CollectionTimingPolicy.CalibratedProduction` replaces the provisional values: overall 60 s, per-operation 10 s, cleanup allowance 2 s, later-operation reservation 10 s, final bookkeeping reserve 500 ms, connect 2 s and frame 8 s. Each is finite, none maps to `INFINITE`, and the reservation split is unchanged. Values were selected from measured standard-user healthy maxima on one unchanged laptop (4.30 s driver operation, 4.00 s result transfer/validation, 0.111 s worker startup to Ready, 0.028 s cleanup) with explicit documented margins; they are engineering calibration, not population percentiles, and no public timeout option exists. `CollectionTiming` records only safe stage/operation names and durations through an opt-in sink that is null in production.

Six fresh non-administrator repeat collections passed schema, privacy, semantic and before/after execution-fingerprint checks, and three live console `CTRL_C_EVENT` runs each returned `3` with no export and no surviving process. See [validation evidence](../VALIDATION.md) for the full record and the one-laptop hardware scope. The only remaining gate is the independent final GPT checkpoint-readiness review; the M4 commit is not authorized by this phase.

### Final review corrections — 2026-09-22

F1 replaces the count-only cancellation controller with an atomic lifecycle. Active collection transitions once to cancellation or output committed. A cancellation winner is published before token signaling and vetoes all report preparation/preview/export; an output winner cannot subsequently become cancelled. Second/reentrant events and captured callbacks entering after output commitment permit ordinary/default termination. Failure closes active collection. The actual CLI boundary commits before handler removal, and gated tests exercise both winners and in-flight token signaling. No new report state, exit code or worker cleanup path is introduced.

F2/F3 use a private, normally disabled lifecycle sink to mark validated attempts and capture process birth identities before signaling, then check tracked workers independently after CLI exit. Timing begins immediately around the successful console-signal call, with readiness/discovery/attachment outside the interval. Healthy checks persist both fingerprint lists around each separate CLI process, as well as a named batch baseline. Separate processes establish repeated startup/deployment success, not same-host admission reuse; deterministic supervisor/admission tests establish reuse after confirmed cleanup and blocking after poison.

F4/F5 leave every production timing constant unchanged. The historical 4299.02 ms operation maximum is inclusive of the 4002.36 ms terminal-frame wait and cleanup; those are not additive. The first Ready receive is not the connect-budget boundary. The 2 s connect margin remains engineering judgment supported by component timings; 500 ms final bookkeeping is an unmeasured conservative reserve, unrelated to worker cleanup or report/export. The 2 s cleanup allowance is approximately 71 times 28.02 ms. The corrected validation record defines segment nesting, exact historical medians/baselines and fresh whole-CLI evidence.

Fresh validation passed 270 tests, the existing schema/native/privacy/timing/helper regressions, seven CLI checks, three controlled first-interrupt runs, one normal control and three healthy runs. No tracked worker survived those corrected scoped runs. Complete evidence stays ignored and private. These corrections support independent final checkpoint-readiness re-review; they do not grant M4 completion or commit authorization.
